# mikto — devlog

> **Версия:** mikto **0.1.0-beta** — первый публичный релиз (см. CHANGELOG.md). Всё, что описано ниже,
> соответствует именно ей: версия в коде, CMake и баннере единая.
>
> Документ написан по коду (не по памяти и не по рекламе): полная схема сканирования,
> все 15 модулей, каждый источник данных, каждое ограничение. Цель — чтобы читатель
> (в том числе человек со стороны) понял, как сканер работает изнутри, что он ищет,
> чего он принципиально не делает и куда его разумно развивать дальше.

---

## 1. Что такое mikto

mikto — консольный сканер **разведки и аудита** для целей, на тестирование которых есть
явное разрешение. Один бинарник на C++20, без внешних зависимостей кроме OpenSSL
(vendored `nlohmann/json` приложен), без скриптов, без рантайма, без API-ключей
по умолчанию.

Он отвечает на восемь вопросов по цели:

1. Что это за цель и какая у неё инфраструктура? (DNS, субдомены, ОС, соседи по IP)
2. Какие сервисы и технологии на ней запущены? (порты, баннеры, веб-стек, версии)
3. Какие CVE реально присутствуют — и на каких именно хостах и портах?
4. Какие сервисы опасно открыты без аутентификации и где лежат секреты?
5. Какие админки, дебаг-эндпоинты и **все остальные разделы** существуют? (в т.ч. скрытые
   пути вида `/api/lol/admin`, которые нельзя найти «словарём по входу»)
6. Что о цели говорят открытые источники? (сертификаты, архивы, e-mail, репутация)
7. Насколько защищён почтовый домен? (SPF/DMARC/DKIM/MTA-STS/TLS-RPT/DNSSEC — модуль `emailsec`)
8. Как всё связано между собой — и что изменилось с прошлого скана?
   (граф разведки с provenance и уверенностью; `mikto diff` между двумя отчётами)

mikto **обнаруживает** проблемы, но никогда их **не эксплуатирует**.

## 2. Контракт безопасности (зашит в архитектуру)

Каждый модуль подписан под четырьмя правилами (`include/mikto/module.hpp`):

| Правило | Что означает на практике |
|---|---|
| Никогда не расширяет scope | Модуль трогает только цели, принятые на CLI. Найденные SAN-имена сертификата, субдомены, соседи по IP — **фиксируются в отчёте, но не сканируются**. Добавить их в scope — явное человеческое решение. |
| Только чтение | Никаких POST, логинов, брутфорса, payload'ов. Единственное, что mikto когда-либо отправляет цели: TCP connect, HTTP **GET** (никогда HEAD), TLS ClientHello, Redis `PING`, read-only служебные запросы (`stats`, BSON `hello`, `/version`), DNS-запросы, WHOIS по TCP/43. |
| Каждая находка — Finding | Серьёзность, модуль, хост, порт, локация, доказательство, рекомендация. Ничего не «просто печатается в консоль». |
| Модуль можно пропустить | Зависимости объявлены и запускаются автоматически; отказ одного модуля не валит скан (try/catch в оркестраторе). |

Плюс два системных ограничителя:

- **Token-bucket лимитер** (`rate_limiter.cpp`): один общий на все HTTP-запросы и
  TCP-подключения. По умолчанию 100 операций/сек, в `--deep` — 800.
- **Честность о видимости скана**: если перед целью стоит WAF/антибот/лимитер, mikto
  не пытается «проскочить» — он ставит хосту метку `scan_visibility: degraded|blocked`
  (модуль `waf`), чтобы никто не принял отфильтрованную картину за полный аудит.

## 3. Полный ход сканирования: от argv до отчёта

```
argv
 └─ parse_cli()                          src/cli.cpp — флаги, дефолты, env-фоллбэки
     └─ parse_target_list()              src/target.cpp — IP / хост / URL / файл списка
         └─ [если --deep] этический шлюз  src/main.cpp — предупреждение + «yes» / --yes
             └─ run_scan()               src/orchestrator.cpp
                 ├─ план = выбранные модули + транзитивные зависимости
                 ├─ HttpClient + RateLimiter(token bucket) + Progress (живой прогресс-бар)
                 ├─ 14 модулей в каноническом порядке (раздел 3.5)
                 │     каждый модуль: try/catch, тайминг → module_timings,
                 │     находки → ScanResult.findings, трафик → ScanResult.traffic
                 ├─ sort_findings()        серьёзность ↓ → модуль → хост
                 └─ отчёты: console (всегда) + JSON/HTML (по флагам --json/--html)
```

### 3.1 Разбор командной строки

Команды: `scan <цель|файл> [...]`, `modules` (таблица модулей с зависимостями), `help`.
Полный набор опций:

| Опция | Дефолт | Что делает |
|---|---|---|
| `--deep` / `--safe` | safe | Расширяет порт-диапазон и включает глубокие пробы; требует подтверждения |
| `--modules a,b,c` | все | Запустить только выбранные модули (зависимости добавятся сами) |
| `--ports 80,443,8000-8100` | авто | Свои TCP-порты (дедуп + сортировка, лимит 70000) |
| `--json <файл>` | выкл | Машинный JSON-отчёт |
| `--html <файл>` | выкл | Автономный HTML-отчёт |
| `--severity info..critical` | info | Фильтр консольного вывода по серьёзности |
| `--concurrency 1..64` | 8 (deep: 48) | Параллельные воркеры |
| `--rate 1..10000` | 100 (deep: 800) | Лимит подключений+запросов в секунду |
| `--timeout` | 1.5s (deep: 1.0s) | TCP connect-таймаут |
| `--http-timeout` | 10s | Таймаут HTTP-запроса |
| `--user-agent` | `mikto/0.1.0-beta (+responsible use)` | Свой User-Agent |
| `--trace` | выкл | Лог всего трафика: каждый HTTP/DNS/TCP/TLS/WHOIS-запрос и ответ (и в отчёты) |
| `--cache-dir` | `~/.cache/mikto` | Каталог дискового кэша OSINT/CVE |
| `--nvd-key` / `NVD_API_KEY` | без ключа | Ключ NVD (выше бюджет запросов CVE) |
| `--shodan-key` / `SHODAN_API_KEY` | без ключа | Полная Shodan API (без ключа — бесплатный InternetDB) |
| `--censys-key id:secret` / env | без ключа | Censys Search API (software/CPE обогащение) |
| `--no-color`, `--no-progress`, `--verbose`, `-y`, `-h`, `-V` | — | Служебные |

### 3.2 Разбор целей

`target.cpp` принимает IP, имя хоста, URL (`https://host:8443/path`) и текстовый файл
со списком строк-целей. Несколько целей обрабатываются одним сканом; порт из URL
учитывается веб-модулями. Скоуп не расширяется никогда — только то, что ввёл оператор.

### 3.3 Этический шлюз глубокого режима

`--deep` открывает полный диапазон 65535 портов и глубокие пробы. Перед запуском —
явное предупреждение о заметности для операторов цели и требование ввести `yes`
(или флаг `-y` для неинтерактивного запуска). Это единственный «агрессивный» режим,
и он всегда осознанный.

### 3.4 Оркестратор (`orchestrator.cpp`)

- Строит **план**: выбранные модули + все их транзитивные зависимости
  (например `--modules cve` подтянет `ports`, `tech`, `infra` с предупреждением
  «enabled automatically as a dependency»).
- Создаёт общий `HttpClient` и `RateLimiter`; модули получают их через `ModuleContext`,
  у которого есть:
  - `get(url)` — лимитированный GET с записью TrafficEvent в лог трафика;
  - `fetch_web(url)` — **кэш страниц на весь скан**: страница запрашивается не более
    одного раза, результат общий для `tech`, `headers`, `waf`, `webpaths`, `secrets`;
  - `pstage/ptick/pitem/pdone` — живой прогресс-бар по стадиям каждого модуля;
  - `trace()` — событие трафика (модуль, тип, цель, запрос, ответ, байты, мс).
- Каждый модуль выполняется в try/catch; падение модуля — предупреждение, скан
  продолжается. Время каждого модуля пишется в `module_timings` и попадает в отчёты.
- В конце: `sort_findings()` (серьёзность ↓ → модуль → хост), фиксация времени.

## 4. Модули — все 15, подробно

### 4.1 `assets` — DNS-рекон + TLS-сертификат

Первый модуль скана; собирает фундамент для всех остальных.

- **Собственный DNS-клиент** (без внешних библиотек, `dns.cpp`): запросы A, AAAA, MX,
  NS, TXT, SOA, CAA; для IP-целей — PTR. Fallback на `getaddrinfo`, если системный
  резолвер недоступен.
- **Анализ политик**: SPF (перечисляет почтовые отправители), DMARC (политика
  `p=none` — находка), CAA (кому разрешено выдавать сертификаты).
- **Проверка «висящих» записей**: MX/NS, которые не резолвятся (зона мусорится,
  возможен takeover).
- **Deep-режим**: попытка AXFR-трансфера зоны на каждый NS (read-only; корректный
  сервер просто откажет — но если примет, это критическая находка).
- **TLS-сертификат** (`tls.cpp`, OpenSSL): Issuer, срок действия, SAN-имена, цепочка.
  Находки: самоподписанный, истекающий/просроченный, wildcard. SAN-имена
  **записываются в отчёт, но не сканируются** (см. контракт).

### 4.2 `whois` — данные регистрации домена

WHOIS по TCP/43 (сначала IANA-реферрал, затем авторитативный сервер) — «голый»
протокол, без API и ключей. Достаёт: регистратора, даты создания/обновления/окончания,
контактные e-mail, nameservers. Находка: домен скоро истекает. Модуль кладёт данные
в `host.whois` (структура `WhoisInfo`).

### 4.3 `subdom` — пассивный поиск субдоменов

Четыре ключевых источника без API-ключей, опрашиваются **параллельно** (по `jthread`
на источник):

1. **crt.sh** — Certificate Transparency логи (`?q=%25.<domain>&output=json`);
2. **urlscan.io** — поисковый API по домену;
3. **HackerTarget** — hostsearch;
4. **Wayback Machine** — CDX API по `*.<domain>` (до 4000 записей).

Из ответов `extract_hostnames()` достаёт хостнеймы под корневым доменом, затем
параллельно проверяет, какие до сих пор резолвятся. Детект **wildcard-DNS**
(заранее проверяется случайное имя — если оно тоже резолвится, значит A-запись
«на всё» и перечисление бесполезно без фильтра). Найденные субдомены попадают
в `host.subdomains` и **не подключаются**.

### 4.4 `emails` — сбор e-mail (в духе theHarvester, без ключей)

Два источника: поля SAN/контактов сертификатов (через crt.sh) и публичные страницы
самой цели (mailto-ссылки + текстовый regex `extract_emails()`). Только адреса
на домене цели; мусорные (картинки-заглушки вида `@2x`) отфильтрованы. Ничего
не верифицируется и не проверяется на существование — только сбор из публичного.

### 4.5 `ports` — TCP connect scan + nmap-стиль лестница проб (reference)

**Сканирование**: неблокирующий TCP connect с таймаутом. Safe-режим — кураторский
набор из **57 портов** (21, 22, 23, 25, 53, 80, 110, 111, 135, 139, 143, 389, 443,
445, 465, 587, 636, 993, 995, 1433, 1521, 2049, 2181, 2375, 2376, 2379, 2380, 3000,
3306, 3389, 4200, 5000, 5432, 5555, 5601, 5900, 5984, 6379, 6443, 8000, 8008, 8009,
8080, 8081, 8443, 8843, 8888, 9000, 9090, 9200, 9443, 11211, 15672, 27017, 27018,
50000, 61616). `--deep` — все 65535. `--ports` — свой список.

**Лестница проб на каждом открытом порту** (в порядке дешевизны):

1. *Пассивный баннер* — для протоколов «сервер говорит первым»: SSH (`SSH-2.0-OpenSSH_9.6p1 Debian-2ubuntu3`), FTP/SMTP-приветствия, MySQL binary greeting, POP3/IMAP, VNC RFB (`RFB 003.008`);
2. *TLS ClientHello* — на TLS-портах (в deep — на любом порту, вдруг TLS там, где не ждёшь);
3. *HTTP GET* — только GET: совместимость сильно лучше, чем у HEAD;
4. *Redis `PING`* — если до сих пор ничего не определено.

Каждая проба повышает **confidence** идентификации:

| Уровень | Метка | Значение |
|---|---|---|
| 0 | `guess` | Только совпадение с таблицей известных портов |
| 1 | `banner` | Эвристика по баннеру |
| 2 | `header` | Из HTTP-заголовка (Server, X-Powered-By) |
| 3 | `confirmed` | Протокол подтверждён рукопожатием/ответом |

**Разбор мульти-продуктовых заголовков**: `Server: Apache/2.4.41 (Unix) OpenSSL/1.1.1d`
даёт два продукта (Apache 2.4.41 + OpenSSL 1.1.1d) и подсказку ОС `Unix`. Из SSH-баннера
достаётся подсказка ОС (`Debian-2ubuntu3` → debian/ubuntu), которая питает `os_guess`.

**Анализ обмана (v0.5, «detection hardening»)**:

- *Несоответствие протокола*: порт 22 отвечает HTTP, 443 без TLS, «DB-порт» говорит HTTP → порт-форвардинг, прокси или фронт-энд другого сервиса.
- *Фейковые порты / honeypot*: сигнатуры баннеров Cowrie, Kippo, Dionaea, OpenCanary и др.; неправдоподобно старые SSH-баннеры.
- *Sinkhole-прокси*: ≥3 открытых порта с байт-в-байт одинаковыми ответами → это wildcard-обработчик reverse-прокси/балансера, а не N независимых сервисов (`sinkhole_groups()`).
- *Forwarding-прокси*: HTTP 407 + `Proxy-Authenticate`, заголовок `Via:`, `X-Squid-Error`.

Всё это попадает в PortInfo (`probe`, `confidence`, `os_clue`, `extra_versions`) и в
находки — чтобы оператор не поверил ложной карте портов.

### 4.6 `infra` — инфраструктура через ключевые источники

Три пути данных, **все без обязательных ключей**:

1. **Shodan InternetDB** (`internetdb.shodan.io`) — что Shodan уже видел для IP: открытые
   порты, CPE-строки, известные CVE-id, хостнеймы, теги. Опционально `--shodan-key`
   апгрейдит до полного host API (ОС, баннеры продуктов).
2. **Geo/ASN** — `ipwho.is` с фолбэком на `ip-api.com`: страна/регион/город,
   координаты, ASN и организация-владелец сети.
3. **Репутация** — лента abuse.ch **URLhaus** (CSV свежих вредоносных URL): проверка,
   не засветился ли IP/хост.

Опционально `--censys-key` добавляет Censys Search API v2: ПО и CPE по каждому
сервису, метки (cloud/datacenter), ASN, rDNS. Найденные CVE-id обогащаются из
датасета **CVE.org cvelistV5** (raw.githubusercontent, без ключа): CVSS, серьёзность,
описание. Данные кладутся в `host.geo`, `host.infra_tags`, `host.shodan_cpes`,
`host.reputation`.

### 4.7 `neighbors` — соседи по IP

Reverse-IP через HackerTarget + хостнеймы, которые Shodan InternetDB уже вернул
для этого IP. Фильтр правдоподобных доменов, дедуп. Зачем: shared hosting — это
общее ядро, сеть и часто панель управления; компрометация соседа может перелиться
на цель. Список — в `host.neighbors`.

### 4.8 `tech` — WhatWeb-стиль фингерпринтинг (161 маркер)

Пассивные маркеры по заголовкам и телу страниц, полученных из общего кэша:

- веб-серверы/прокси, CDN/WAF-эджи;
- CMS: WordPress, Joomla, Drupal, Bitrix, OpenCart, Magento и др.;
- языки и фреймворки: PHP, ASP.NET, Java/Tomcat, Rails, Django, Flask/FastAPI, Express, Next.js, Nuxt;
- JS-библиотеки **с версиями**: jQuery, React, Vue, Angular, Bootstrap, Lodash, Alpine, htmx;
- базы данных: по строкам SQL-ошибок, админ-тулингу **и уже открытым портам** (MySQL/MariaDB, PostgreSQL, MongoDB, MSSQL, SQLite, Redis, Elasticsearch);
- хостинг-панели: cPanel, Plesk, ISPmanager, aaPanel/BT, Webmin.

Активная часть — только read-only GET-ы к известным эндпоинтам, раскрывающим
версии. Результат — в `host.tech` (имя, версия, источник «header:X-Powered-By» /
«body:wp-content») плюс `host.os_guess` по собранным баннерам. Всё это — сырьё
для модуля `cve`.

### 4.9 `webpaths` — универсальное обнаружение контента (reference, главное в v0.6)

До v0.6 модуль ходил по кураторскому словарю — и мог пропустить `/api/lol/admin`,
потому что «lol» не бывает в словарях. Теперь это **поисковый движок разделов**,
который находит всё, включая пути, которые никто не догадается перебирать.

**Стадия 1 — сбор сидов.**

- *Soft-404 baseline*: запрос случайного пути `/<rand>-<rand>.miktobase`. Если сервер
  ответил 200 с телом >128 байт — это catch-all (SPA/заглушка), все дальнейшие
  ответы сравниваются с базой.
- *Домашняя страница* — берётся из общего кэша (её уже качал `tech`).
- *robots.txt* — `parse_robots_entries()`: пути из `Disallow:`/`Allow:` (wildcard
  вырезается; записи с остаточными `*` отбрасываются) + локации `Sitemap:`.
- *sitemap.xml* — `parse_sitemap_locs()`: все `<loc>` того же хоста, включая **один
  уровень вложенных sitemap-индексов** (до 2 файлов).
- *HTML домашней страницы* — `extract_page_paths()`: значения `href`/`src`/`action`/
  `data-*`, пути из CSS `url(...)`, same-host абсолютные URL; query и фрагменты
  срезаются.
- *JS/CSS-литералы* — до 3 файлов (deep: 6) скачивается, и из строковых литералов
  достаются пути: `fetch("/api/lol/admin")`, axios-роуты и т.п.
- *Майнинг слов* — `extract_path_words()`: из путей и camelCase/snake_case-токенов
  (`adminPanel` → `admin` + `panel`); стоп-слова (HTML/JS-клей: `window`, `function`,
  `display`...) отфильтрованы, правдоподобные существительные (`admin`, `config`,
  `backup`) специально оставлены. Хранится до 80 слов (deep: 160).
- *Кураторский словарь* — 74 пути в safe, **217 в deep** (панели, CI-конфиги,
  debug-бары, CMS-внутренности, Spring Boot actuators, логи, API-доки, БД-тулзы).

**Стадия 2 — проба сидов.** Только GET. Дедуп между источниками с приоритетом
(сайт сослался сам `link` > `js` > `robots` > `sitemap` > `wordlist`); статические
ассеты, уже видимые на странице, не перепроверяются; ответы сверяются с soft-404
базой.

**Стадия 3 — две рекурсивные волны комбинаций.** Это ядро, которое ловит
`/api/lol/admin`:

- каждый подтверждённый 200-путь без расширения становится **кандидатом в директории**,
  а **каждый его сегмент** (≥3 символов) — новым словом для комбинаций (`note_hit()`);
- `generate_discovery_candidates()` строит кандидатов пяти семейств:
  `dir + suffix` (`/api/` + `admin` → `/api/admin`), `word` (`lol` → `/lol`),
  `dir + word` (`/api/` + `lol` → `/api/lol`), `word + dot-suffix` (`lol` + `.env` →
  `/lol/.env`), `word + suffix` (`lol` + `admin` → `/lol/admin`);
- словарь суффиксов — **101 слово разделов** (admin, login, config, backup, api,
  v1/v2/v3, swagger, actuator, credentials, jenkins, webmail...);
- волна 1: до 800 кандидатов (deep: 1200); волна 2: до 500 (deep: 800); директорий
  в комбинации — до 64 (deep: 96), мелкие первыми (`/api/` раньше `/api/lol/`);
- **тела новых подтверждённых страниц снова майнятся** (до 3 за волну) и добытые
  из них ссылки и слова уходят в следующую волну — так поиск «расползается»
  вглубь сайта сам.

**Как именно ловится `/api/lol/admin`**: если `/api/` подтверждён как директория,
а «lol» встретился хоть раз в скрипте или в ссылке — волна 1 пробует `/api/lol`
(dir+word) и `/lol/admin` (word+suffix); подтверждение `/api/lol/` даёт новую
директорию, и волна 2 пробует `/api/lol/admin` (dir+suffix). Путь не из словаря
найден.

**Честность (никаких «и так далее»)**:

- каждый подтверждённый путь записан в `host.paths` с полем **source** — «как найден»
  (wordlist/link/js/robots/sitemap/combo), со статусом и размером тела;
- инвентарь — до 600 путей на хост; если больше — точное число переполнения
  **считается и предупреждается**, ничего не исчезает молча;
- находки — до 100 на URL, переполнение тоже честно посчитано и указано;
- итоговая Info-находка «Content discovery confirmed N surfaces» содержит разбивку
  по источникам (link: X, js: Y, combo: Z...);
- классификация каждой находки — `classify_path()` + человекочитаемое описание
  и рекомендация: source/secret file, debug endpoint, actuator, admin surface,
  API docs, backup archive, login surface и т.д.

### 4.10 `exposed` — сервисы без аутентификации (reference)

Проверяет, какие службы отвечают **без логина** — строго read-only:

Redis (`PING`), Memcached (`stats`), MongoDB (BSON `hello`), Elasticsearch,
CouchDB, etcd (`/version`), RabbitMQ management, Docker API (`/version`),
Kubernetes API (`/version`). Ничего не пишется, ничего не обходится; открытый
без аутентификации сервис — находка с доказательством-баннером.

### 4.11 `headers` — HTTP security headers (reference)

Берёт веб-эндпоинты из общего кэша (страница качается один раз на весь скан) и
прогоняет через чистую функцию `analyze_security_headers()` (unit-тесты отдельно
от сети): HSTS, Content-Security-Policy, X-Frame-Options, X-Content-Type-Options,
Referrer-Policy, Permissions-Policy, флаги cookies (Secure/HttpOnly/SameSite),
раскрытие версий в Server/X-Powered-By, доступность и редирект HTTPS. Каждая
находка — с конкретной рекомендацией по заголовку.

### 4.12 `waf` — что стоит между сканером и целью (preview)

Отвечает на вопрос «насколько полон этот отчёт»:

- *пассивно*: подсказки WAF/CDN по заголовкам и cookies; фингерпринт блок-страниц
  по статусам 403/406/429/501/503 (`classify_block_page()` — Cloudflare, Imperva
  и др.); антибот-челленджи (Cloudflare «Just a moment», PerimeterX, DataDome,
  Kasada, queue-страницы); rate-limiter по 429/`Retry-After`; geo-блоки.
- *активно*: ровно **один** дополнительный GET с безобидной строкой `?id=1 AND 1=1`
  на веб-цель. Никаких payload-наборов и обходов.

Результат — метка `host.scan_visibility`: `full` / `degraded` (что-то мешало:
лимитер, geo-блок) / `blocked` (антибот-челлендж) + список причин
`visibility_notes` + Info-находки с именем эджа. mikto принципиально **не
пытается обойти** блокировку — он честно говорит, что видел отфильтрованную
картину.

### 4.13 `cve` — версии → CVE по точному месту

Собирает список продуктов из четырёх источников:

1. `ports` — баннеры сервисов (OpenSSH, nginx, MySQL...) **+ вторичные продукты**
   из мульти-продуктовых Server-заголовков (OpenSSL из примера выше);
2. `tech` — веб-стек с версиями (WordPress, PHP, jQuery, БД...);
3. `infra` — сырые CPE-строки Shodan/Censys.

Дальше — **онлайн NVD 2.0** (без ключа; с `--nvd-key` — выше лимиты): 24-часовой
дисковый кэш в `--cache-dir` для повторных сканов, самотемпинг, ответ 429 → пауза
на одно окно и ровно один повтор, бюджет запросов на скан: **15** без ключа /
**60** с ключом — чтобы большой инвентарь не подвесил скан. Сравнение версий —
своя функция `compare_versions()` (числовые сегменты численно, буквальные суффиксы
выше числового префикса: `9.6p1` > `9.6`).

Каждый совпавший CVE привязывается к **точному хосту и порту**, где продукт
наблюдался (не «где-то на сервере»), с CVSS/серьёзностью/описанием и публичными
ссылками на эксплойты из индекса **Exploit-DB** (raw.githubusercontent, без ключа).

### 4.14 `secrets` — утечки учётных данных (preview)

Сканирует уже скачанные тела страниц (общий кэш — новых запросов почти нет) плюс
небольшое число JS того же origin. Набор паттернов — **намеренно консервативный**,
высокоточный: AWS access key id / secret key, Google API key, Stripe, Slack-токены,
приватные ключи-заголовки и др. Широкие шумные правила («всё, где есть password=»,
энтропийные сканеры) сознательно не включены: ложные срабатывания убивают доверие
к отчёту быстрее, чем пропущенный ключ. Чистая функция `scan_body_for_secrets()`
покрыта unit-тестами.

### 4.15 `emailsec` — гигиена почтового домена (preview, новое в v0.7)

Полностью DNS-модуль (пассивный, read-only). Ключевое решение: **не дублировать**
`assets` — тот уже сообщает об ОТСУТСТВИИ SPF/DMARC/CAA и неразрешаемых MX/NS.
`emailsec` оценивает КАЧЕСТВО опубликованных политик:

- **SPF-политика**: `+all` (критично — подделка разрешена всем), отсутствие `all`
  (высокая — подделки проходят), `?all` (низкая), превышение лимита DNS-lookups
  RFC 7208 (>10 → permerror, SPF фактически не работает), приватные/loopback-диапазоны
  в `ip4:` (признак копипасты), несколько `v=spf1`-записей (permerror);
- **DMARC-политика**: `p=none` (только мониторинг — подделки не блокируются),
  отсутствие `rua=` (нет обратной связи), `pct<100` (часть писем без проверки),
  `sp=none` (субдомены не защищены), битые записи без `p=` (высокая);
- **DKIM**: проба 16 распространённых селекторов (`google`, `default`, `selector1`,
  `s1`, `k1`, `mail`, …) — находка «подпись подтверждена» либо честная «на
  распространённых селекторах не найдено» (нестандартный селектор возможен);
- **MTA-STS** (`_mta-sts`, RFC 8461) и **TLS-RPT** (`_smtp._tls`, RFC 8460) —
  защита от STARTTLS-downgrade и видимость TLS-сбоев;
- **DNSSEC** (DNSKEY на апексе) — без подписи зоны SPF/DKIM/DMARC сами подделываемы;
- позитивные заметки о CAA, когда записи есть.

Живая проверка на `example.com` возвращает ровно его реальную политику:
SPF `-all`, DMARC `p=reject`, DKIM-селектор `google`, зона подписана.

## 6. Модель данных (`scan_result.hpp`)

Один агрегат `ScanResult` наполняется модулями и целиком съедается репортерами:

- **HostResult** (на каждую цель): `ips`, `ports[]` (PortInfo с `probe`/`confidence`/
  `os_clue`/`extra_versions`), `tls`, `os_guess`, `tech[]`, `paths[]` (PathHit с
  `source`), `subdomains[]`, `wildcard_dns`, `emails[]`, `neighbors[]`,
  `infra_tags[]`, `shodan_cpes[]`, `dns_records[]`, `dns_zone_transfer`, `geo`,
  `whois`, `reputation[]`, `scan_visibility` + `visibility_notes[]`.
- **Finding**: severity (info/low/medium/high/critical), module, host, port, service,
  location, title, detail, recommendation, evidence.
- **TrafficEvent**: модуль, вид (http/dns/tcp/tls/whois), цель, строка запроса,
  строка ответа, статус, байты отправлено/получено, время — весь диалог сканера
  с целью.
- **WebResult**: статус, заголовки, server, title, усечённое тело для скана секретов.

## 7. Отчёты (3 репортера)

**Console** (`console.cpp`) — всегда. Дерево «хост → сервисы/находки», цвета по
серьёзности, списки с честными капами, одна итоговая строка; фильтр `--severity`.
Цель: вся картина за 10–15 секунд чтения.

**JSON** (`json_report.cpp`) — по `--json`. Машинный формат без усечений: все
субдомены, записи DNS, заголовки, пути, события трафика. Поле к полю совпадает
с моделью из раздела 6.

**HTML** (`html_report.cpp`) — по `--html`. Один автономный файл: inline CSS +
ванильный JS (без зависимостей), работает офлайн через `file://`, без внешних
шрифтов, фреймворков и CDN. Всё динамическое HTML-экранируется. **Ничего не
обрезается**: каждый субдомен, каждая запись, каждый заголовок, каждый путь,
каждое событие трафика рендерится; большие объёмы организованы progressive
disclosure — `<details>`, фильтры, sticky-навигация. Секции: Overview,
Findings, Hosts, Web responses, **Correlations**, Traffic, Scan info. Оценка
риска: взвешенная сумма находок (critical=25, high=10, medium=4, low=1) →
0–100 → грейд A (clean) / B (low) / C (moderate) / D (elevated) / F (high).
Светлая/тёмная тема (prefers-color-scheme + ручной переключатель), табличные
цифры, контраст 4.5:1, focus-visible, reduced-motion, print-стили.

Информативный слой v0.7 (всё, что раньше было только в JSON):

- **Correlations** — интерактивная карта интеллект-графа: canvas, радиальные
  кольца по типам сущностей, цвет = статус (confirmed/probable/possible/
  unverified), подписи хабов, tooltip с provenance при наведении, перерисовка
  при смене темы/размера окна; кап 120 хабов указан. Ниже — полные таблицы
  сущностей и связей с фильтрами (тип/статус/связь/текст), шкалами confidence
  и тегами источников; клик по сущности фильтрует её связи. Капы 2000/4000
  как в JSON, всегда указаны.
- **Панель внешних провайдеров** (Scan info): запросы/успехи/провалы/блокировки/
  trips breaker'а/состояние на конец скана.
- **Матрица security-заголовков** (Web): ✓/✗ по CSP, HSTS, X-Frame-Options,
  X-Content-Type-Options, Referrer-Policy, Permissions-Policy для каждого
  полученного URL + оценка n/6; колонка Content-Type в таблице ответов.
- **Overview**: шкала состава балла риска, бары находок по модулям (клик —
  фильтр), чипы учёта (подавленные дубликаты, вытесненные события трейса,
  запросы к провайдерам), чипы entities/relations.
- **Traffic**: честная пометка «показано N из M» при переполнении буфера и
  топ-5 самых медленных запросов.
- **Hosts**: счётчики tech/paths/subdomains/DNS прямо в шапке хоста.

## 9. Честные ограничения (что mikto НЕ делает и где границы)

1. **Safe-режим = 57 портов.** Полный диапазон только в `--deep` (осознанно).
2. **Словари.** Встроенный список — кураторский, не SecLists-размера. Движок
   комбинаций закрывает «длинный хвост» путей, но внешние мега-словари пока не
   подключаются (`--wordlist` loader — в планах).
3. **CVE — онлайн.** Без сети модуль cve не работает (для повторных сканов —
   дисковый кэш; бюджет запросов ограничивает очень большие инвентари).
4. **Субдомены и SAN-имена не сканируются** — только фиксируются (контракт scope).
5. **Нет headless-браузера.** SPA-роуты добываются из JS-литералов; рендеринг
   JavaScript и клики по интерфейсу не выполняются.
6. **Нет аутентификации.** Логины, cookies, обход авторизации, брутфорс, эксплойты
   — принципиально вне скоупа (см. docs/RESPONSIBLE_USE.md).
7. **Одна точка наблюдения.** Geo-блокировка может показать другой контент, чем
   видит оператор из другого региона; mikto это помечает (scan_visibility), но
   с одной машины не эмулирует.
8. **Капы вежливости.** Пути: 600/хост в инвентаре, 100 находок/URL, слова 80–160,
   кандидаты 800–1200/волну. Все капы — с честным подсчётом переполнения и
   предупреждением, но это капы.
9. **Качество сторонних датасетов** (crt.sh, HackerTarget, Wayback, InternetDB)
   вне контроля mikto; источники задублированы и парсятся консервативно.

## 12. Что добавлено в v0.7 — intelligence-движок (новейшее, см. также CHANGELOG.md)

Это самый крупный сдвиг архитектуры со времён v0.2: mikto научился не только
«собирать находки», но и **объяснять, как всё связано, насколько этому можно
верить и что изменилось с прошлого раза**.

### 12.1 Граф разведки (Intelligence Graph)

После отработки всех модулей оркестратор складывает весь `ScanResult` в типизированный
граф сущностей (`intel_graph.hpp/cpp`). 12 типов вершин: домены, IP, ASN, провайдеры
(CDN/WAF/регистратор/репутационные ленты), сервисы `host:port`, технологии, эндпоинты,
e-mail, сертификаты, MX, NS, CVE.

Главное — **честность**: у каждой вершины и ребра есть источники, уверенность 0–1 и статус:

- `confirmed` — прямо наблюдённый факт: DNS-ответ, подтверждённый протокол на порту,
  реально ответивший эндпоинт;
- `probable` — сильное одиночное наблюдение: фингерпринт по заголовку/телу (его можно
  подделать), запись из сторонней базы;
- `possible` — вывод или непроверенное совпадение: ASN из гео-lookup, CVE без
  подтверждённой версии, соседи по IP;
- `unverified` — заявлено источником, здесь не проверялось.

Сущности сливаются ТОЛЬКО по совпадению (тип, нормализованное значение): соседи,
разделяющие IP с целью, **никогда** не приписываются цели. В JSON отчёте — секция
`intelligence_graph`, в консоли — одна строка с итогом.

### 12.2 `mikto diff` — что изменилось между сканами

```bash
mikto scan example.com --json mon.json
mikto scan example.com --json tue.json
mikto diff mon.json tue.json --html diff.html   # exit 0 = без изменений, 1 = есть
```

Показывает новые/исчезнувшие субдомены, IP, открытые порты, смены версий технологий,
изменения DNS-записей и сертификатов, новые/исправленные находки — с метками
first_seen/last_seen и подсказками серьёзности (новый критичный findings — сверху).
Код возврата 1 при изменениях = готовый мониторинг в cron/CI.

### 12.3 Здоровье внешних провайдеров + circuit breaker

Каждый запрос к стороннему API теперь учитывается: запросы, успехи, сбои, блокировки.
5 транспортных сбоев подряд (или лимит 60 запросов на провайдера за скан) открывают
circuit breaker — дальнейшие запросы к умершему источнику пропускаются, результаты
деградируют честно, каждый блок попадает в JSON-секцию `providers`. `mikto providers`
печатает каталог всех 14 источников с эндпоинтами, env-переменными ключей и
документированными лимитами бесплатных тарифов.

### 12.4 SARIF и CSV

`--sarif report.sarif` — SARIF 2.1.0 (совместимо с GitHub code scanning),
`--csv findings.csv` — плоская таблица находок с RFC 4180-экранированием. Итого 5 форматов:
консоль, JSON, HTML, SARIF, CSV.
